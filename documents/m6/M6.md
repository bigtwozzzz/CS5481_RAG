The matrix, manifest, and freeze steps are in `documents/m6/M6_EXPERIMENT_PLAN.md`. Dev and holdout run records are under `results/m6/`. The gateway did not return a context limit.

The Chinese records in `../中文/` stay outside this repository.

## Retrieval experiment

The run is on the new dev set only: `data/evaluation/inputs/m5_dev.questions.jsonl`, SHA-256 `868b4a198b4cce5570ab6c1d341e8ec641b0b95cff9fbe3ceeec71b96813751e`. Gold SHA-256 is `a9ef3d34d8d968eb545f7252b1a42da0ffbf3e24f1124d49e7e671cf96c04184`. All 15 questions were retrieved. Coverage uses the 12 answerable questions and their 18 gold quotes. `m5_dev_003`, `m5_dev_006`, and `m5_dev_015` are saved and excluded from the rates below.

Controlled conditions: one corpus (3152 documents in `.local-m4`), one embedding model (`sentence-transformers/all-MiniLM-L6-v2`, revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`), `candidate_k=30`, RRF constant 60, and an M4 evidence budget of 1024 tokens on the embedding tokenizer. The grid is strategy A/B/C, Dense/BM25/Hybrid, and k=3/5/10. k=3 and k=5 are prefixes of one live top-10 search. Both packing policies were applied to the same prefix. There were 135 live searches and no generation API call.

A quote is covered when a chunk from the gold evidence document contains that quote in full. All 18 quotes fit inside a chunk in every strategy index, so a miss is ranking or budget. The five rates are macro averages over the 12 questions:

- Hit@k: questions with at least one covered quote.
- Evidence Recall@k: covered quotes divided by that question's quotes, then averaged.
- Complete@k: questions whose quotes are all covered.
- MRR@k: reciprocal rank of the first covering chunk, or 0.
- Document hit rate: the gold evidence document appears in the list.

### Three evidence stages

Raw candidates are `retrieval.results`, before the 1024-token packer. M4 packed evidence is `selected_chunk_ids` after `legacy_break_v1` or `skip_continue_dedup_v1`. The evidence sent toward M5 is the list `build_context` keeps for the built-in `deepseek-flash` input budget: the 16 KB UTF-8 guard and the 8192-token application limit, including the 1600 output reserve and 512 safety margin.

`scripts/m6_evaluation/score_three_stage_evidence.py` recomputed all 54 saved directories after `load_a_run` checked each run's status, file hashes, and evidence binding. It checked 648 answerable rows. On every row, the chunk list that would be sent into M5 is the same list M4 selected. The generation budget does not remove another chunk after the M4 packer. The machine-readable copy is `results/m5/d_dev_retrieval/three_stage_summary.json`. That file records the gold hash, the three prompt hashes, and the hash of the built-in `deepseek-flash` budget profile used for the third stage.

At this input-preview stage, the generation model and its price were not yet frozen. The preview uses the built-in tokenizer profile and is not a completed G0, G1, or G2 answer run. The CityU profile was still a candidate then. It uses the same tokenizer assets and the same 8192-token application limit. The later dev run froze that model and per-call budget; the price is still unknown. The Chinese record of that run is `../中文/M6_中文.md`, outside this repository.

### Raw candidates

Raw metrics do not change with the packing policy. Each setting is a `conditions` entry in `results/m5/d_dev_retrieval/summary.json`. B with BM25 and B with Hybrid cover every answerable question at k=3. C with BM25 and C with Hybrid reach raw Complete 12/12 at k=5. A with Dense stays 10/12 through k=10. Incomplete question ids in that file omit nothing: they use the full `m5_dev_` id.

### M4 packed evidence and the M5 input

On all 648 rows, the M5 input metrics equal the M4 packed metrics. The settings where those two stages are lower than the raw candidates, and the questions the budget newly drops, are in `results/m5/d_dev_retrieval/three_stage_summary.json`. Every other setting keeps the raw Hit, Recall, Complete, MRR, and document hit after both the M4 packer and the M5 input preview. Both packing policies agree on these five rates. The new packer keeps one extra chunk on 22 of 324 answerable rows, and that extra chunk does not change the five rates.

For B/Dense/k=5, `m5_dev_002` is already incomplete in the raw candidates. The budget newly drops `m5_dev_009`. After the budget, the incomplete questions are 002 and 009. At k=10, both questions are complete in the raw list, and the budget drops both.

`m5_dev_002` is the budget bottleneck. Under C/Hybrid/k=5 its second quote is raw rank 5, and appending that chunk needs 1207 tokens, above the 1024 M4 budget. B/BM25 and B/Hybrid already contain both quotes inside the top 3, and both fit, so all three stages stay at Complete 12/12.

The packed bundles keep about 3 chunks and about 860–950 M4 embedding tokens. That size fits the local M5 input check, which is why the third stage does not drop coverage again.

## G0, G1, and G2

The comparison uses the same 15 dev questions and the saved bundle `m5_runs/d_dev_retrieval/C_hybrid_k5_skip`. The model is `CS5351/DeepSeek-V4-Flash`. The three runs use the same per-call budget profile, `configs/m5_budget_cityu_cs5351.json` (`m5-token-budget-cityu-cs5351-v1`): an 8192-token application limit and a 512-token safety margin on each call. That is not a shared total compute budget. The built-in `deepseek-flash` profile stays in place. The scoring guide is `documents/m6/ANSWER_SCORING_v1.md`.

G0 loads `g0_prompt_citation_v1.txt`, which asks for a citation inside the answer text. It does not run a citation hard check, support review, or repair. G1 uses structured output from `generation_v1.txt`, then hard citation validation, and the passing draft is the final answer. It does not review or repair. G2 follows that generation path, then support review and at most one repair.

An offline fixture with a mock model kept the same evidence chunk list and the same model string across the three paths. G0 stopped after one generation call, G1 stopped after one validated generation call, and G2 made the generation call and the review call. A dry run, `run_pipeline(..., allow_repair=False)`, and a G2 file whose review fields were deleted did not pass the G0 or G1 check.

The scored run is `m5_runs/m6_dev_protocols_20261122T165403/`, with new directories `G0`, `G1`, and `G2`. Each batch status is COMPLETE, the ledger check passed, and `check_answer_scores.py` reported 0 errors on each filled sheet. COMPLETE, a matching ledger, and 0 check-script errors show that the run finished and the records agree. They do not show that the answers are correct, and the script does not replace the human reading of the answers.

An earlier directory, `m5_runs/m6_dev_protocols_20261122T165339/`, failed on every item with `NETWORK_ERROR` before the gateway was reachable. It is kept and is not part of the scores below.
